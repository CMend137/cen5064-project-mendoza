# ADR-003 — Replace JSON persistence with SQLite history

**Date:** 2026-11-07  
**Status:** Accepted  
**Supersedes:** ADR-002 for new application data

## Context

The midterm stored only the latest calculated nutrition targets in `data/targets.json`.
Every calculation overwrote the previous values, so users could not inspect,
edit, or delete calculation history or retain daily intake and weight records.
The professor requested a relational database and an expanded graphical UI.

## Decision

Use Python's built-in `sqlite3` library with a local `data/macrometric.db` file.
`data/target_repository.py` owns SQL, schema initialization, and all database
connections. The Streamlit presentation tier uses `TargetService` and
`ProgressService`, which delegate persistence to the repository. The domain
modules calculate targets and evaluate progress without SQL or UI dependencies.

Tables:

- `calculations`: integer primary key, UTC creation timestamp, the original
  inputs (weight, height, age, sex, activity level, goal), and calculated
  calories/protein/fat/carbohydrates. New calculations append rather than
  replacing a previous calculation; records can be listed, retrieved, updated,
  and deleted by ID.
- `daily_logs`: one entry per ISO date, daily weight and calorie intake.
  Saving the same date updates the existing entry. Entries can be listed and deleted.

Database writes use SQL parameter binding and transactions. Data files are
ignored by Git. `TargetStore` is an abstract storage contract used by
`TargetService`, preserving the dependency inversion introduced in PR #8.

## Alternatives considered

- **Continue using JSON:** simplest, but inadequate for relational history,
  records with stable IDs, robust updates and queryable time series.
- **Hosted database (PostgreSQL):** scalable but adds service provisioning,
  credentials, and deployment complexity for a local student application.

## Consequences

**Benefits:** Local, durable history; no database server, credentials or new
Python database packages; structured queries and straightforward test isolation
using temporary database files; CRUD support through service methods.

**Trade-offs:** A local SQLite file is currently single-profile; the
application does not include authentication, access control, multiuser sync, or
production backups. We start with new SQLite data rather than automatically
migrating the old single `targets.json` result. Recommendations are explicitly
simple rules, not clinical advice. A future release should formalize schema
migrations and multi-user data ownership if needed.

## Validation

`tests/test_sqlite_repository.py` verifies history across repository instances,
update/delete, and daily log upserts. `tests/test_progress_service.py` verifies
weekly summarization and input validation. Run `python -m pytest -q` and open
all five Streamlit tabs to demonstrate the new workflows.
