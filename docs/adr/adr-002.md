# ADR-002: Persist calculated nutrition targets in local JSON

**Date:** 2026-10-11  
**Status:** Accepted

## Context

MacroMetric's midterm working slice lets a user enter body measurements, sex, activity level, and a fitness goal, and calculate personalized daily calorie and macronutrient targets. The course requires a screen → logic → storage → screen flow, and the most recently calculated result should remain visible after refreshing or restarting the Streamlit app.

Configuring a database or external service would add complexity for this single-user, local prototype. We want a clean-clone setup that requires no database credentials, while keeping file handling out of the presentation and domain layers.

## Decision

Store the **latest calculated target result** as JSON in the locally generated `data/targets.json` file. Encapsulate file operations in the `TargetRepository` class (`data/target_repository.py`). Its `save()` method creates the directory if needed and writes the targets, and `load()` retrieves the stored values or returns `None` if the file does not exist.

The Streamlit UI (`app.py`) invokes `TargetService` (`services/target_service.py`), which calls the domain function `calculate_targets()` (`domain/target_calculator.py`), persists the result through `TargetRepository`, and reloads it for display. The UI and domain calculator do not directly read or write the JSON file.

## Consequences

**Benefits:**

- The complete working slice runs without a database server, credentials, or network dependency.
- Targets remain available after page refreshes or application restarts.
- The repository class isolates storage implementation and makes future replacement feasible.
- The JSON file is easy to inspect during the midterm demo.

**Trade-offs and risks:**

- Only the **latest** result is saved; there is no historical intake, body-weight, or multi-user store yet.
- A local JSON file is unsuitable for concurrent writes, multi-user production use, or sensitive data storage.
- This implementation does not provide atomic writes, schema migration, or recovery from corrupted JSON.

**Follow-up:** Add persistence and error-handling tests. When implementing daily logs and weekly trends, reassess whether JSON remains appropriate or whether a database such as SQLite is justified; document any new choice in another ADR.
